# Agent work and status follow-up v1 — T7CF442AE

This is the concrete revised producer contract. The early `contract.md` and
`examples/overview.json` remain immutable draft evidence; use this document,
`schemas/agent-work-v1/contract.schema.json` and `examples/v1/` for integration.
The schema's `$defs` name exact register, mutation, overview, follow-up and list
shapes. Output objects allow additive fields; request objects reject unknown and
duplicate members, malformed UTF-8/JSON, trailing data and files over 16 KiB.

## Operations

Every command accepts `--workspace PHYSICAL_ROOT --format text|json`. Root is
otherwise discovered from cwd. `--json` selects result JSON; explicit text conflicts
with true `--json`. Success writes one JSON object and newline; failure exits
nonzero, writes the stable error code on stderr and no result on stdout.

| Command after `ply workflow` | Request | Result/effect |
| --- | --- | --- |
| `agents` | none | `AgentWorkReadback@1`, fresh bounded Herdr list plus native registered sources and follow-ups; read only |
| `followup register --file FILE` | `RegisterRequest` | `AgentFollowup@1`, one durable registration, no send |
| `followup list [--due]` | none | `AgentFollowupList@1`; read only |
| `followup show ID` | ID | current `AgentFollowup@1`; read only |
| `followup request ID --file FILE` | `Mutation` | makes an unconsumed cycle due, or explicitly opens a new status cycle after fulfilled; no send |
| `followup dispatch ID` | ID | claims and sends at most one fixed message per cycle |
| `followup recheck ID --file FILE` | `Mutation` | explicit recipient self-report; waiting creates a new cycle |
| `followup cancel ID --file FILE` | `Mutation` | closes follow-up, no send |
| `followup retarget ID --file FILE` | `Mutation` | explicit new target generation; consumed cycle stays consumed |
| `followup request-status ID --request-id REQUEST` | stable mutation ID | original applied result, without replay; `show` returns current state |

A server due loop is explicitly opt in: call `list --due`, then `dispatch ID` for
each listed ID. Commands are bounded, synchronous, and start no daemon, model or
session. Time passing, missing replies and transport ACK never open a new cycle.
A working target remains due but deferred. Repeating the same deferred reason
creates no additional revision. Clients may poll on their existing service timer.

## First action from an agent row and authority

`target_ref` is exactly the row's `agent_ref`. For a first explicit human status
request use `wait_kind: "status"` and `wait_ref: agent_ref`, choose a stable
`publication_key`, and register with the current UTC time. Then explicitly
`request` that returned ID if needed and `dispatch` it. A view refresh never
registers, requests or dispatches. The row's `followup_refs` identifies existing
ID/revision/generation/cycle subjects; `capabilities` has the same exact subject.

`owner_ref`, `mandate_ref` and registrar `actor_ref` are safe caller-selected
references to actual authority held by the local caller/server. They are not
native Run/session IDs, tokens, guessed Task mandates or a new product authority.
The server uses its authenticated human/Slack/owner-socket authorization and
preserves that real request's provenance as `human_requested`. An agent registering
its own technical wait uses `agent_self_registered`. CLI declarations are not
identity authentication; these commands run with the invoking local user's store
access. Knowing an owner reference is not remote authorization. The server must
never expose this as a public HTTP control interface.

An agent row's register/first_request capability is `unknown` until the caller
supplies actual authority, or `disabled` if execution identity is incomplete.
Unbound agents can be registered and reminded with explicit authority. An agent
self-registration must use its target_ref as registrar.actor_ref. Fresh complete
runtime identity and complete relevant native question/stop coverage with no
matching veto permit the fixed reminder, without inventing a Task or Run. Missing
or partial veto coverage remains unknown and sends nothing. This limitation is
intentional and does not prevent a status read. Existing follow-up capabilities
bind the exact ID, target, revision, generation and cycle. Enabled means the
operation's local preconditions permit a request; dispatch still revalidates.

## Readback, idempotency and limits

Canonical follow-up ID derives from owner_ref, mandate_ref, wait_kind and wait_ref.
It excludes publication aliases and target generation. Retrying unchanged register
input returns current state; a different publication alias with the same canonical
contents resolves to the same ID. Changed contents conflict. Global publication
keys cannot be reassigned to another obligation. Recover a lost register response
by replaying the same bytes or `list` and exactly matching that four-field tuple;
then verify registrar, target and chosen check time. Do not guess a new key/ref to
retry consumed work. For status requests, always use the canonical status wait_ref
above, including across UI action IDs and service restarts. A status registration
also checks the existing owner/mandate target lineage: retargeting cannot bypass a
consumed obligation by registering the new agent_ref as a separate UI action. It
returns followup_status_target_already_registered; use the existing followup_refs.

A stable mutation request_id binds its operation and every request field. Retry
returns the original result even after later revisions. `request-status` finds
that original result; not recorded returns `followup_request_not_recorded`, which
is a read observation, not proof about an unrelated dispatch. Dispatch uses the
follow-up's stable `transport.cycle_ref` rather than a UI action ID; after a lost
send reply use `show ID`. Never resubmit a different logical obligation to retry
an unknown send.

Mutation core fields are request_id, owner_ref, expected_revision and generation.
Recheck requires the exact target_ref and outcome waiting/fulfilled/cancelled;
provide bounded done/next/blocker or summary text. Waiting requires an explicit
next_check_at_utc. Retarget requires target_ref. Cancel and request need core fields
only. Wrong owner/revision/generation is `followup_revision_or_owner_conflict`;
changed bytes under a used request_id are `followup_request_conflict`. Cancelled and other closed
follow-ups reject mutations with `followup_closed`; a fulfilled status follow-up
accepts the explicit new-cycle request described below. Still-waiting consumed requests return
`followup_cycle_consumed`. A successful request-status does not authenticate a
reporter or claim that native product QA passed.

A recipient's fulfilled status report closes that control, not the user's ability
to request status again while native work continues. Reuse the same follow-up,
owner/mandate/target and canonical status wait_ref. Submit `request` with a new
stable request_id and the current expected_revision/generation. Only this explicit
owner action can reopen a fulfilled **status** follow-up. It archives that cycle's
transport and recipient report in `history`, opens the next cycle as waiting/due
with a new cycle_ref, and sends nothing until dispatch. Retrying the identical
request reads back its original result; concurrent requests using the old revision
conflict. Register, show, list, refresh, time passing and repeated dispatch never
rearm a fulfilled follow-up.

Each history entry contains cycle, original transport/dispatch_subject, and that
cycle's recipient recheck. It never rewrites sent/unknown or native work/QA state.
The current `recheck` remains the last recipient report and may belong to a previous
cycle; its explicit cycle field and text label distinguish it from the new pending
control. Both JSON and every relevant text readback retain summary-only answers.
Still-waiting consumed/unknown cycles and cancelled follow-ups cannot use this
new-cycle request path. A matching recipient must first explicitly report fulfilled
(or waiting with a new technical check time); owner aliases, new IDs and target
generations cannot substitute for that receipt.

At most 4096 agents, 512 follow-ups, 128 applied mutation IDs and at most 128 archived cycles per follow-up, and
8 MiB per durable store revision are supported. Agent-source overflow is partial;
registration/mutation store limits fail with explicit errors, never silent
truncation. Refs use the schema's ASCII patterns, at most 128 characters; public
metadata and each report text field are at most 256 UTF-16 code units. Dates are
RFC3339 UTC with Z. Inputs are caller-intended public report text; do not include
secrets or private paths. All registrars and reports are explicit provenance,
never inferred human judgment.

## Observation, native work and transport

`pane`, `tab` and `workspace` preserve safe actual Herdr IDs for status-v1
compatibility. `agent_ref` hashes provider/native session/workspace/tab/pane/terminal
and changes on execution replacement. Public output never copies sessions,
terminal IDs, paths, terminal titles, tokens, prompts, transcripts or raw source errors.
Herdr list/get are bounded to ten seconds and eight MiB per output stream, using
no transport cache. `observed_at_utc` is a read time; nullable source observation
time stays null when Herdr supplies none. Available/empty/partial/unavailable
and freshness remain separate. Own recognized codex/claude agents include those
without Tasks; incomplete execution identities remain unknown and cannot send.

`Agent.tab_label` is optional presentation metadata (T965226AF). It comes only
from public `herdr tab list --workspace ID`, `result.tabs[].label`, joined by
exact workspace/tab. It never contributes to identity, refs, follow-up generation,
claims, vetoes or transport targets. Missing/empty/whitespace-only, invalid or
duplicate/conflicting labels are omitted, with existing source status, freshness
and capabilities preserved. Names are untrusted plain text, valid UTF-8, at most
256 Unicode codepoints, without terminal controls/ANSI. Invalid
names are omitted rather than repaired or truncated; terminal titles and launch
labels are never fallbacks. Older producers omit the field; older consumers
can ignore it. See `examples/v1/overview-tab-label.json`.

Each Overview shares one metadata read per workspace across its existing agent
rows: lexically first 32 workspaces, at most four parallel commands, 256 KiB each
for stdout and stderr, and 4096 tab records per response. A shared one-second
deadline includes queuing and reads; subprocess pipe cleanup adds at most 50 ms
concurrently across workers. No retry, extra inventory/history read or request
cache is used. Rename appears on the next Overview; a close/rename race can
retain the last observed name without creating an identity claim. Get, follow-up
reads/registration and dispatch do not read this metadata.

Verified work is joined only on all execution identity fields to native registered
attempts, with Project/Repo/Epic/Task/Run/attempt_ref and a safe `workflow.trace:ID`
detail reference. Phase, next_actor, next_action kind/reason and nullable native
source activity time remain registered facts. Private native action text is not
copied; a safe reason directs the consumer to native detail. Work is derived on
read, not persisted as a Task-status copy. Done agent turn and fulfilled recheck
never establish delivered Task, completed review, human QA or integration.

Before input: exact fresh target identity, idle/done, positive interactive_ready,
no launch_pending, intact relevant native veto coverage, no current human question,
inactive lifecycle, unresolved stop/refusal/unknown effects or QA veto. Herdr's
documented omitted launch_pending=false is honored; missing readiness fails
closed. Unknown relevant native veto coverage prevents sends. Unrelated historical
diagnostics remain partial source metadata and are scoped to their independently
verified session; they do not become another target's veto. Unidentifiable or
changing identity sources still make coverage unknown. For a bound attempt the
registered phase must permit a status reminder; for an unbound runtime, a complete
question and registered-attempt/stop scan must have no matching session veto or
conflicting former binding. This is a scoped native-source observation, never
proof that a provider has no undisclosed pause or that work may resume. Reads still work.

Transport.dispatch_subject is null before claim. At claim it permanently records
the attempted agent_ref, followup_id, revision, generation and cycle. Retarget
changes the current follow-up subject while preserving that original dispatch
subject, for both sent and unknown. Never attribute an old attempt to the new target.

Dispatch serializes native follow-up mutations, revalidates, then durably publishes
unknown/possibly-sent before the first input. Crash after claim, timeout, lost ACK
and incomplete response retain unknown and forbid replay, including aliases,
request IDs, target generations and process restarts. ACK becomes sent/queued,
never read or handled. Recipient must `show` and revalidate ID/target/generation/
cycle/waiting before checking fresh actual status and posting a recheck. A waiting
recheck is one explicit separate action opening a new cycle. After a fulfilled
status report, a later revision-bound owner request is the other supported path. It grants no authority
to retry refused work. Herdr get→prompt is best effort, not atomic; the session may
change or input queue between calls. This producer makes no turn-CAS claim.

## Consumer handoff and executable evidence

Use the CLI through the server's fixed service adapter, not Go imports or `.ply`
reads. Preserve HTTP status-v1 `version: 1.0`, actual pane metadata, 4096/256 limits,
response observation, Tailscale login and Firebase CORS. Rich work/follow-up data
uses its separate version above. TUI's private owner socket and Slack share that
service. No HTTP/PWA action, app restart or deployment is included.

`examples/v1/` contains actual deterministic Go serialization: human registration,
request, deferral, sent without recheck, unknown/no replay, waiting/fulfilled,
retarget while consumed, cancellation, bound/unbound and partial overviews.
The status-summary-fulfilled and status-explicit-new-cycle fixtures show the
revision-bound recurring status journey and preserved prior-cycle history.
`go test ./internal/agentwork` compares these frozen fixtures to exercised behavior.
The exact make-built candidate is tested by `TestStatusFollowupCandidateJourney`
with fake Herdr and a disposable native workspace. This exercises public CLI
register/list/recovery/dispatch/recheck/request-status and privacy without live
foreign agents or server activation. The frozen acceptance entrypoint runs these
bounded focused checks; it does not claim installed CLI or production app QA.
