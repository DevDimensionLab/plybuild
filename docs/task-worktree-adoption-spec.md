Status: proposed product contract, source-checked at `fe77e90e4d971c4eb52b5e00241c61d48a81751f`.
AL44 produces this design; a separately selected implementation Goal is required to implement it.
Sections 1–7 describe future product behavior. Section 8 records only this planning Task's delivery boundary.

## 1. User outcome and existing support

An operator has useful clean committed work in a local linked Git worktree, outside Ply ownership. They want one active Task to own that exact path and branch, then start an ordinary fresh execution and deliver to its registered Epic. Binding must neither move Git nor invent a past owner, start, result, test, review, QA or delivery. The first cut supports a previously unused Task and one supplied first Goal, with an automatic local Epic delivery agreement. It does not reopen an old Task.

## 2. Supported scope and public interface (future)

One new entry point, from the registered Epic return checkout:

```text
ply workspace task worktree adopt TASK_ID \
  --project PROJECT --repo REPO --epic EPIC \
  --path /physical/existing-source --ref refs/heads/useful-work \
  --expected-oid SOURCE_OID --format json
# Read-only preview. Repeat identical inputs plus:
# --apply --confirmation sha256:<preview digest>
```

Task ID and scope must match an existing active, unused Task. First register its supplied Goal using existing `workspace task goal register` preview/apply; a new Task may be created by that helper. Adoption itself never creates a Task/Goal, changes the Problem, selects an executor or starts an agent. The exact first Goal must be pending in this Epic queue, with current Problem, intact documents and automatic `local_epic_integration` delivery to this Epic. Adoption pins that Goal reference. Legacy execution/solution Specs, human-gated and other delivery modes are outside this first cut. They remain supported through existing non-adoption journeys.

Required operator input is the intended Task, target scope, physical source path, full local branch ref and expected current commit. Compute tree, common-dir, worktree inventory, Goal hashes, base version, native IDs and writer evidence internally. Use existing registry-upgrade conventions if required; never ask for manual session/permission/hash attestation files. Preview is read-only; apply's confirmation selects these exact observations and ownership transfer. It grants no provider permissions or blanket future authority.

Scope requirements:

- Source is a physical, existing, clean linked worktree of the exact registered repository; full local branch ref, exact expected OID/tree, common-dir and inventory agree. No untracked changes or in-progress Git operation. No symlink alias, detached ref, nested/overlapping Task/return directory, main repository source, Epic target path/ref, or branch checked out elsewhere.
- Task/Epic are active. Task has no prior worktree, worktree operation, preparation, result, Run/start/owner or release/closeout/retirement history. No reparenting, migration or reuse of an old Task ID. Preserve all historical records and retirements.
- The registered current Epic base `B` is observed clean and exact at preview and apply. Source `S` is a descendant of `B`, `S != B` and its tree differs from `B` (useful committed delta). First cut does not infer semantic usefulness from the diff. No adoption of already delivered work: if `S` is ancestor/equal to current Epic head, reject. No Git reset, merge, cherry-pick, rebase, checkout, worktree creation/removal or ref movement occurs during adoption.
- No historical or current Task/Epic binding, intent, preparation, Run source, closeout reservation or retirement resource record claims the source path/ref/worktree identity, including inactive history. An old source never becomes “unowned” just because its process exited or cleanup retired a resource. Compare canonical path overlaps and common-dir/ref pairs. Multiple logical Epics sharing a target are supported, but their target is never a Task source.
- No current preparation or unresolved target effect is allowed for this queue. Pending entries may precede/follow the adopted Goal: adoption preserves every rank and does not occupy the current slot. It reserves only this source and Task. Ordinary execution subsequently selects it explicitly, or selects it when naturally next. Other queues are not globally locked.

### Readback and stable request

Return a proposed `ply.workspace.task-worktree-adoption` JSON record: schema version, phase (`preview`, `reserved`, `adopted`, `blocked` or `unknown`), Task/project/repo/Epic IDs, exact Goal revision/hash, worktree/operation IDs after reservation, confirmation/intent digest, source path/ref/common-dir/OID/tree, parent worktree/ref/base revision/OID/tree, `origin=adopted`, observation/provenance timestamp, queue ID/revision and disposition, writer observation with limitation, reason codes, effects, and `next_argv`/`check_cwd`. Successful apply has `git_effects=[]`, `agent_started=false`, `qualified=false`; never populate a Run/result/QA field with an invented ID.

Extend existing `workspace task show TASK_ID --format json` to show immutable adoption and separate fresh source/parent observations, reservation/outcome and execution linkage. Queue list must report adopted Goal eligibility without pretending execution is prepared. Plain text carries the same reasons/next step. A completed identical retry returns the original receipt and separately current freshness; a changed source does not erase adoption history.

## 3. Ownership, persistence and recovery

Clean Git is not writer absence. Apply must obtain fresh native evidence scoped to the source: managed pane/agent inventory and bounded local cwd writer observation using existing adapters. Generalize only the necessary source-path observation from `taskWriters`/`observeWriterLiveness`: no invented session for an unregistered source, no machine-wide approval registry. Retain the current limitation: a process that left the cwd and holds/names no known session can be unobservable. There is no proof against arbitrary external editors. Report this limit rather than claiming absolute absence.

Source must be idle. The command runs from the Epic checkout; exclude only the command and its verified children, never an arbitrary source pane/process by operator assertion. A known managed owner, pending start, local source writer or ambiguous inventory blocks transfer. Unknown inspection or runtime refusal blocks this action with a sourced reason and “restore supported read access/stop the actual owner, then recheck this same intent”. Do not add a permission confirmation, poll live providers, clear old refusals, or call runtime/ps/lsof in this planning Task. Recheck ownership before later start and cleanup too. An adoption receipt is not an ongoing lease against outside Git edits.

Use the existing workspace registry lock/CAS and native resource reservations. Add a versioned adoption operation alongside current creation operations, with an explicit discriminant; do not serialize adoption as a successful Git create. Reserve Task, physical path and common-dir/ref together. Reuse ID generation, canonical digests and store publication recovery. Pin stable request fields (scope, Goal, source/start, current base and source provenance); incidental readback timestamps must not change the request key. Do not build a parallel journal/lock platform. Extend strict store/schema/closure validation for the new operation; old-format registries and old creation semantics remain unchanged through supported version upgrade.

Apply order:

1. Validate preview digest and current registry/Goal/queue/resource identities under native locks; reobserve Git and scoped writer state. Fail before reservation on a known mismatch.
2. Persist immutable adoption intent/reservation with source `S` and parent `B`, provenance and observations. No Git effect begins.
3. Reobserve source, parent and ownership, then publish adopted binding/outcome atomically under the same registry publication mechanism. A ready binding has source `oid/tree = S`, `parent_oid/tree = B`, `origin=adopted`, exact operation/digest and new exclusive worktree ID. Preserve original Git origin as “observed existing”; do not claim Ply authored the commits or know their original fork point.
4. Return durable receipt and next execution check. Adoption itself adds no queue event and does not materialize an execution Spec.

Crash before intent: same input previews/applies normally. Crash/lost reply after intent: read back same operation first, then resume only its finalization after reobservation. Crash after outcome: return preserved success without republishing or touching Git. Changed inputs for a reserved Task/path/ref conflict and name the original operation; do not allocate another identity. Concurrent competing adoption/create/start must lose the same reservation CAS. Foreign queue reorder or base/Goal change invalidates an unfinished preview; never restore a stale queue snapshot.

If observation after reservation differs or is unknown, retain the reservation as blocked/unknown and show exact mismatch/next step. No automatic retry, cancellation, rebind or new owner. Same intent may resume when its exact observed basis is restored and writer evidence is available. If it cannot be restored, v1 leaves it blocked for a separately designed recovery; this is an explicit unsupported recovery case, not authorization to patch the store. An adopted but unstarted binding whose source/base/Goal subsequently changes is likewise not silently repinned. This narrow limitation is preferable to weakening immutable start facts.

## 4. Usable Goal, start and delivery path

The following are implementation obligations, not behavior already supplied by current Ply:

1. **Register Goal before adoption.** Existing first-Goal helper keeps its unbound guards. Adoption binds only its exact pending Goal. Do not add “register first Goal on arbitrary bound Task”.
2. **Execute check consumes adoption.** Extend Goal evaluation and `PreviewTaskGoalExecution` only for this completed adoption and pinned Goal. Use its existing branch/path rather than generated names. Verify `S/B` unchanged, scope, clean inventory, current base, reservation and owner absence. Bind the delivery agreement to the actual source ref. Returned execution preview explicitly shows `source_mode=adopted`, source/start `S`, parent `B`, and cleanup effects. It performs no start or extra worktree creation.
3. **Prepare/start from that preview.** `PrepareTaskGoalExecution` materializes a fresh execution revision, assessment/selection and existing native preparation/queue-current transition using that adoption. Remove only this Goal from pending, retain foreign order, require no current slot, and store the normal execution request receipt so lost replies recover the same preparation/Run. Link preparation outcome to adopted worktree and `S`; bypass Git create only for this discriminated source mode. Legacy `task prepare` still cannot materialize a Goal; it must return the normal execute guidance. No blanket removal of bound-Task guards.
4. **Carry two identities end to end.** Execution `implementation_basis.parent_oid/tree = B`, `start_oid/tree = S`. Update execution plan/preparation typed schemas, origin validation (`validateExecutionGoalOrigin`), [generic basis validation](../internal/workspace/task_spec_guard.go) (`validateSpecImplementationBasis`), store validation and `ShowTask` freshness to compare source with start, parent with base. The generic basis guard already accepts a descendant start when a Task is bound; reuse that ancestry/freshness support and bind its start explicitly to the adoption receipt. Existing creation records default to `start=parent`; no old bytes rewritten. Initial handoff/target/receipt freezes actual `S` and exact source ref/path/common-dir. The fresh runtime owner receives all Goal requirements, the existing delta and its provenance to assess/adapt/test. Native session and per-action runtime decisions are freshly observed. No transfer of old session/mandate or evidence.
5. **Ordinary exact qualification.** Owner commits under the new mandate as needed, makes the private candidate, uses separate native review on this Run and exact `verify`. `CurrentDeliveryTaskSpec` must accept the exact clean adopted start; `ValidateDeliveryCandidateTarget` must continue requiring a clean candidate descended from `S`, unchanged execution basis and parent `B`. Inherited commits are included in review/test scope; their mere existence is no technical pass. Failed/changed candidate requires correction and fresh review/verification. Preserve actual later human veto even with automatic acceptance.
6. **Integrate and close.** The selected automatic local Epic agreement permits only native fast-forward integration from actual source ref into observed `B`, after current exact qualification. Reuse integration reservation/effect observation, queue advancement, append-only Epic base update, retained artifacts and native closeout. No second integration effect after unknown outcome. The execution preview/start mandate must explicitly include ordinary source cleanup, including this pre-existing adopted branch/path; adoption alone authorizes no deletion. On owner handoff the owner exits; coordinator follows from the return checkout, establishes writer absence, retains evidence/archive identity, removes the now-owned source through native cleanup and observes closure. If cleanup fails, integration may be observed while closure remains pending; preserve the same operation and continue only supported recovery. Historical adoption remains readable after removal.

Moved-base policy is deliberately small. Before adoption, explicitly refresh the Epic using supported base preview/update if live head is ahead; then require the refreshed `B` to be ancestor of `S`. Record it as the **chosen execution parent**, never an assertion about the source's original start. If `S` diverges from refreshed base, report `adoption_base_not_ancestor` and retain source; reconcile it outside this adoption or use an eligible fresh-copy route. After adoption/execute freeze, a moved base blocks start/qualification/integration under existing stale-base checks. Do not amend an old binding/execution to chase the base; a later recovery design or fresh Task copy is required. A normally unchanged parent still permits the complete journey above.

## 5. Small worked scenario and fault boundaries

Model in an isolated fixture: Epic `E` at `B`, active Task `T` with first Goal `G`, pending order `[U,T,V]`, no current slot. Existing unowned source `/repo/useful` on `refs/heads/useful` is clean at `S=B+two commits`, distinct tree. Inventory and writer adapter report idle.

Preview/apply adoption pins `G,S,B`; Git objects/refs/worktrees and queue ranks are unchanged. Readback says adopted, not prepared/started/qualified. A lost apply reply returns the same worktree/operation IDs and receipt. Explicit execute of `G` previews that exact source and cleanup, creates a normal fresh execution/preparation/current slot, leaving pending `[U,V]`. Owner starts at `S`, produces clean descendant `C`, obtains separate review and exact automatic pass, then integrates `B→C`. Queue current closes, Epic base appends `C`, retention preserves original source references, and coordinator follow removes the source after owner exit. All earlier fixture Run/Task/retirement records stay byte-identical. No historical source is used as a live test specimen.

| Boundary | Required observation and useful next step |
| --- | --- |
| Dirty/untracked source, in-progress Git, wrong repo/path/ref, detached or duplicate checkout | Reject adoption before intent with the differing identity/status; preserve Git. Resolve that concrete condition and preview again. |
| Released/completed/retired/bound Task or any historical source claim | Reject identity reuse; inspect existing native history. Use supported backup when eligible or supply a genuinely new unused Task and unclaimed source. New Task naming alone cannot bypass a source claim. |
| Known writer or unknown/refused inspection | Block only ownership transfer/start/cleanup that depends on absence. Preserve denial and known effect status. Stop actual owner or restore supported observation, then recheck; clean status is insufficient. |
| Source/base/Goal drifts before apply or unfinished intent finalization | Stale preview fails; a persisted reservation remains bound and visible. Recover same request only on its exact basis, otherwise report unsupported recovery. Never move Git or rewrite historical inputs. |
| Lost reply/publication failure or competing adopter | Observe same intent/outcome before retry. Return durable IDs after success; conflict on competitor; unknown publication remains unknown until observed. Never duplicate current preparation/start. |
| Changed source after successful adoption, stale parent after freeze, review failure, cleanup writer | Show adoption history separately from readiness. Block the dependent action; use ordinary correction/requalification when within the frozen start/parent, otherwise report v1 limitation. Preserve integration if already observed. |

## 6. Implementation seams and regression strategy

Keep one source-mode seam inside existing Task preparation/execution. Add adoption input/preview/operation/service and thin CLI wiring; reuse Git observations, ancestry, registry publication, native queue folding and delivery controls. Strict versioned store/schema changes must represent `S` independently of `B` wherever plans, bindings and evidence are compared. In particular, changing only `Origin` or CLI wiring cannot satisfy this contract. No new approval platform, global development lock, historical migration, generic legacy resumption or manual attestation protocol is required.

Red/green for the future implementation, using existing temporary repositories and injected dependencies:

- Extend [internal/workspace/work_item_test.go](../internal/workspace/work_item_test.go) fixtures with pre-existing clean `S != B`: first demonstrate absent adoption behavior and rejected binding, then test successful metadata-only adopt/retry and competing claims. Assert exact Git inventory/refs/trees and foreign history/queue bytes before/after, not just an exit code.
- Extend [internal/workspace/task_first_goal_test.go](../internal/workspace/task_first_goal_test.go), [internal/workspace/task_goal_execution_test.go](../internal/workspace/task_goal_execution_test.go) and [internal/workspace/task_queue_test.go](../internal/workspace/task_queue_test.go): Goal-first adopt→execute carries `S/B`, consumes only `T`, starts from existing path, and normal create remains `start=parent`. Test Goal/base/source drift and lost publication at intent, binding and preparation. Assert legacy bound/released Tasks remain rejected.
- Extend [internal/taskrun/delivery_task_writers_test.go](../internal/taskrun/delivery_task_writers_test.go) and [internal/taskrun/delivery_writer_liveness_test.go](../internal/taskrun/delivery_writer_liveness_test.go) with injected path-based idle/live/unknown/refused observations; no real provider or process inspection needed. Verify a known owner cannot be excluded by a caller's claim and a failed inspection never becomes absence.
- Extend [internal/taskrun/delivery_default_cleanup_test.go](../internal/taskrun/delivery_default_cleanup_test.go), [internal/workspace/task_closeout_test.go](../internal/workspace/task_closeout_test.go) and [internal/workspace/task_goal_execution_test.go](../internal/workspace/task_goal_execution_test.go) for adopted exact start/candidate, separate review/verify and integration/retention/owner-handoff/follow. Wrong `S`, nondescendant `C`, changed parent and unqualified candidates must fail before delivery. Lost integration reply resumes its effect observation rather than integrating again.

Keep these few end-to-end boundaries and targeted negative subcases, not an exhaustive combinatorial matrix. Run focused regressions first, then existing affected suites as justified by implementation changes. Add CLI help/JSON contract assertions in existing command tests. Red tests must fail for the behavioral gap before production code makes them pass.

## 7. Modeled versus live acceptance

Future implementation acceptance requires the idle fixture scenario through native lifecycle and the fault boundaries above, with exact identity and zero Git mutation at adoption. Modeled writer/provider adapters establish software behavior only. They do not establish live writer absence, runtime access, human judgment or installed support. A later expressly authorized live probe may use a disposable new Task/Goal/source and supported native controls. No actual old Run/source/project mutation, global policy changes, provider probe, historical denied test or store patch is preparation for that probe. AL14/19/25/25B/28/35 refusal history and the AL40 helper gap remain preserved; no design text resolves them by assertion.

A live inability to inspect an idle source is a concrete limitation to report, not grounds for a new human permission form. Remaining risk is external writers beyond the bounded observer and base drift between lifecycle stages. The contract exposes the former and blocks on the latter. Selection of other source histories, divergent-base recovery, released Task resumption, retained adopted-source cleanup options and nonautomatic delivery is deferred. There is no unresolved product choice needed to implement the narrow journey selected here.
